## Trial 96: unchanged hardware parameters, Android handoff fails

Trial 96 kept the exact trial 93 effective DT, kernel, GSI/vendor and
test seeds. `display_bind.sh` adds a small read-only pinconf record before
and after each existing pins/fabric/core stage. It records GPIO20/21/79/80/81
to both the display log and kmsg. No GPIO requests, voltage votes, reset
writes, clock settings, rescan or firmware changes are added.

The intended observation would distinguish inherited high WLAN_EN from a
low-to-high enable transition at fabric probe. The current PMU driver preserves the initial
WLAN enable value, while the board pinctrl lacks explicit output-low.
That is a testable hypothesis, not the diagnosed cause. PCIe power/PERST
ordering and trial 94's separate missing-ADB/reset failure remain open.
On a retained GSI boot, continue targeted inspection there; on failure,
restore the existing F.20 recovery set without another full stock reread.

Actual result: FAIL, boot `b912ef7f-3224-4611-b268-6bc0dbb2f7a6`.
PCIe still reports no link and only the root bridge. The pinconf file prints
pin names, not electrical state, so the enable-edge hypothesis is unmeasured.
The probe is corrected to the GPIO debug show interface already captured in
trial 93; that correction has not yet run on a WLAN-enabled candidate.

The Android guard reaches `armed` at 92.919 s; adbd and SurfaceFlinger start,
and USB gadget binding returns success at 101.535 s. Host ADB never appears.
The retained console stops at 101.560 s without an explicit panic. A recovery
boot follows. This repeats trial 94 with the original 900 mV minimum; the
948 mV vote is therefore not a necessary condition for the failure. Neither
the last SELinux denial nor a specific reset mechanism is proven causal.

F.20 recovery completes with boot `c9b99306-e612-4125-827e-af3af9bf28ff`,

## Next isolation and CPU measurement

Trial 97 keeps trial 96's kernel and the accepted GSI/vendor, display flags,
test seeds and guard. Package without WLAN device-tree additions and require
the effective DT to match trial 90 exactly. This isolates device activation
from kernel binary changes; a single successful boot would narrow the issue,
not establish the precise WLAN fault or prove long-term stability.

On a retained boot, `verify_m3_cpu_dvfs.py` runs four seconds of pinned integer
work on CPU 0, 4 and 7, with idle recovery between runs. It checks same-boot
enforcing/guard identity, unchanged governor/bounds and bounded temperatures.
The native helper verifies affinity and has its own alarm in addition to the
Android timeout. This measures driver-reported frequency response, not
scheduler placement, sustained frame rate or thermal throttling. The helper
compiles with NDK warnings as errors; the device measurement is NOT RUN yet.

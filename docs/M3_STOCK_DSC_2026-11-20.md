# M3：原厂 DSC 编码与面板参数对照

当前目标：消除 ACK 6.18 + Android 17 GSI 的实屏花屏，随后推进 AOSP 桌面。

## trial 65 的补充结论

2026-11-20 用户明确反馈“65轮还是花屏”。该反馈没有区分原生和 Android 阶段，因此只记录本轮实屏失败，不补写两个阶段各自的观察。历史暂停记录保留原样。

复核同次启动 `d156e9a3-246e-4249-a618-54a0931f7aa0` 的已保存快照，31 项配置对照全部通过：DSI CCF bit/byte/pixel 为 660/82.5/110 MHz；PPS、单 DSC 路由、分包寄存器、测试图和固定系统输入与 trial 64 一致。因此，**单独对齐这组链路时钟没有修复花屏**。CCF 读数不代表示波器实测。

复核输入是 `graphics-first-0-display.txt` 的逐字节副本，没有拼接跨启动日志。其 SHA-256 为 `085ae3c76dba7fcfc42b5fef594dca099bcf8a8e3d8af46c34f4571ce406ad01`。详见 [时钟对照](../build/device/m3-linkclock-65-reviewed-2026-11-20.json) 和 [PPS/面板读回](../build/device/m3-readback-65-reviewed-2026-11-20.json)。面板 0x9e 读回仍无可解释的完整 PPS，不能据此宣称面板已接受或拒绝参数。

## 下一轮改变什么

trial 55 将面板收到的 PPS 对齐到 ACK 自动计算的编码器参数；它没有测试“编码器和面板同时采用原厂完整 PPS”。原厂与 ACK 的差异集中在首行预算和最后五组 RC range，由此还产生解码延迟、缩放间隔和后续行预算的差异。

| 字段 | trial 65 ACK 值 | 本次原厂值 |
| --- | ---: | ---: |
| first_line_bpg_offset | 12 | 15 |
| initial_dec_delay | 526 | 594 |
| scale_increment_interval | 1190 | 1059 |
| nfl_bpg_offset | 523 | 654 |

新增默认关闭的 `msm.rmx2072_stock_dsc=1`。保留原厂时钟开关、单 DSC、每包两片、1080×2400@60、540×48 slice、8 bpc/8 bpp。仅调整原厂首行预算及 RC 表，再调用固定版本 DRM helper 计算其余字段。计算出的 88 字节必须与官方 Q 20607 面板 0x9e 原始载荷逐字节相同，否则拒绝该配置。DPU 和面板驱动共享同一 `drm_dsc_config`。

该开关只允许项目 RM19795 panel 节点、SM8250 单 DSI command mode 和已核验的原厂时钟组合。打包器还要求单 DSC 路由及匹配的内核补丁摘要。GSI、项目 vendor、测试卷、DTB/DTBO 和测试图不变。

## 已做验证与真机边界

从实际补丁提取计算函数，与固定 ACK helper 一起编译成纯运算 ARM64 程序，在 F.20 执行。88 字节原厂载荷完全匹配；错误宽度和意外 RC 阈值均被拒绝。该程序不访问显示设备或 MMIO，**不是实屏验证**。见 [计算记录](../build/device/m3-stock-dsc-arithmetic-2026-11-20.json)。

下一轮验收先检查 `RMXDSC stock-pps ... match=1`、实际 DSC 寄存器、完整发送 PPS、DSI 时钟和路由，再观察原生及 Android 实屏。仅计算、构建或 ADB 成功不能作为修复结论。

当前手机保持恢复后的 F.20。显示门控镜像仍需要主机每次放行；本次若继续花屏，采集后恢复 F.20，不再将这种诊断镜像当成可无人值守使用的系统留在手机上。不追加冷启动或看门狗故障注入测试。

## 构建和核验进度

内核 [build 35](https://github.com/xxbo/RMX2072-AOSP-Project/actions/runs/44744298788) 基于提交 `1b43f9a8a80bac4032a6c1c83614e1b3dae543aa` 构建中，尚未刷入新候选。

# RMX2072 development plan

Updated 2026-11-14 for the realme X50 Pro Player Edition (RMX2072, Snapdragon 865 / SM8250). This plan defines progress by what the handset can boot and operate. The [earlier M0–M8 plan](https://github.com/xxbo/RMX2072-AOSP-Project/blob/dfd17d95f25a0cda113af939adaa2be14142d798/plan.md) preserves the source research, legacy builds and original checklists.

## Target system

Boot an Android 17 ARM64 GSI from internal UFS on a project-built ACK 6.18 kernel. Build the RMX2072 device trees, boot ramdisk, device-specific vendor configuration, HALs and required kernel drivers from pinned source. Reuse working upstream drivers and port the board-specific parts. The release must operate independently of the realme Android partitions, F.20 kernel and modules, extracted Android HAL binaries and factory DTB/DTBO. The selected GSI is recorded in [build/gsi.json](build/gsi.json).

| Dependency | Treatment |
| --- | --- |
| F.20 Android, vendor/odm, boot and DTBO | Use for measurements, controlled comparisons and recovery. Identify each borrowed item in a trial and the milestone that replaces it. |
| Board and Android integration | Build the board DTB/DTBO, boot-v2 ramdisk and minimal vendor image from source. Own the fstab, init rules, VINTF declarations, SELinux policy and HAL integration. Test the GSI against this vendor image. |
| Silicon boot ROM, subsequent boot stages, secure world, modem/DSP or peripheral firmware, and calibration | Record each required component separately: source or provenance, who loads it, affected functions and replacement status. Distinguish immutable hardware from replaceable shipped binaries. Any retained factory binary remains an explicit dependency in the release report. A claim of complete factory independence requires evidence accounting for every entry. |

CI builds the artifacts and checks the project vendor for reproducibility. On the handset the [diagnostic probes](https://github.com/xxbo/RMX2072-AOSP-Project/tree/da4385b38212ea8f84307f672a741da77172ecc5/scripts/device_audit) exercise USB, UFS and verified mounts. The [fault recorder](https://github.com/xxbo/RMX2072-AOSP-Project/blob/19d77ebfd3b5c5eed24c49c4494043a9203a12b7/scripts/device_audit/record_init_fault.py) correlates PID 1 mappings with failed block reads. The [M1 vendor recorder](https://github.com/xxbo/RMX2072-AOSP-Project/blob/da4385b38212ea8f84307f672a741da77172ecc5/scripts/device_audit/record_m1_vendor.py) already produces a JSON entry from each saved trial and its recovery evidence. Cross-build failure comparison and the Android test stages below remain planned.

### Failure report and retest

- Emit a short summary and machine-readable results per trial. Record the build and boot identity, test name, expected and observed values, and a timestamp or log reference. Use `PASS` or `FAIL` for executed checks, `BLOCKED` for a missing prerequisite, and `NOT RUN` for checks outside that trial. Identify host, cable or runner errors separately.
- Lead with the first observed failure on each affected path. If the vendor mount fails, attach the mount error and mark dependent HAL tests blocked. Keep independent USB/UFS results visible. Use the early boot transcript before ADB and collect logcat or a bugreport once the required Android services are available.
- After a fix, rerun the failed check, its subsystem tests and the known-good boot/USB/UFS checks. Compare new failures, fixes and remaining failures with the previous comparable build. For a changed build, start a fresh targeted suite run. Within a run on the same build, use the suite retry feature for failed or unexecuted cases.

See [VTS for HALs and kernels](https://source.android.com/docs/core/tests/vts), [CTS execution and retry](https://source.android.com/docs/compatibility/cts/run), [UI Automator](https://developer.android.com/training/testing/other-components/ui-automator) and [Monkey](https://developer.android.com/studio/test/other-testing-tools/monkey).

## Next work after M1 headless acceptance

The [November 13 UFS trial](docs/M1_UFS_FIRST_STAGE.md) reached Android second-stage init on 6.18 with the GSI and project vendor on internal storage. PID 1 verified and mounted both logical partitions and read the complete system build properties and main init script under enforcing.

1. **Complete the source-built TEE Keymaster path.** Trial 25 repaired the post-transaction version regression by moving version/HMAC queries onto the tested whitelist transport and contiguous buffer layout. On the same kernel and boot, the temporary key exercised TIME listener 11 command 770, resumed, was deleted, and the listener was removed; all three version checkpoints returned 0. The project HAL then registered and returned HMAC parameters to GSI keystore2. Keystore2 registered maintenance, and vdc earlyBootEnded exited with status 0. Implement shared-secret computation and HAL key generation, which still return UNIMPLEMENTED and leave boot-level key creation incomplete. Retain the same writable test volumes. The vendor patch date `1970-01-01` is an engineering placeholder and the TIME control uses USB-host UTC. Keep the secure-world firmware provenance explicit. [Trial 25](build/device/m1-ufs-keymaster-transport-2026-11-14.json) · [F.20 callbacks](build/device/m1-f20-keymaster-listeners-2026-11-14.json)
2. **Keep debugging on the accepted GSI baseline.** Trial 35's PDC/PON/PS_HOLD kernel passed disconnected power-key startup, locally retained adbd, enforcing/API 37/second-stage PID 1, verified UFS mounts, the 193.844-second post-reconnect soak and 1 MiB transfer. Its expired-lease fault then independently reset into diagnostics, disabled the recovery watchdog, entered EDL at 176.094 seconds and completed original restoration through the prepared host. No keys or host reboot command were used. The qualified recovery requires a waiting computer; a 45-second unattended EDL hold remains unresolved. Retain GSI for routine work, restoring F.20 for failures or comparisons. [Cold start](build/device/m1-disconnected-start-35-2026-11-14.json) · [Same-kernel recovery](build/device/m1-autonomous-recovery-35-2026-11-14.json)
3. **Replace measured board dependencies in M2.** Build the board DTB/DTBO and ramdisk/first-stage init from pinned source. Replace the temporary legacy PON alias with the source tree's upstream binding. Reproduce M1 on those exact artifacts, including disconnected startup, six UFS LUNs, verified mounts, diagnostics, ADB and watchdog recovery. Retain the explicit boot-firmware/TEE/peripheral firmware dependency inventory. [Power investigation](docs/M1_POWER_CONTROL.md)

After M3, rehearse one Android GSI update with the working kernel, board trees, ramdisk and project vendor held fixed. Compare VINTF, headless boot, desktop and subsystem smoke results against the previous GSI. Record any device-layer changes the new release actually requires.

Each milestone record should identify the source revision, kernel/DT/ramdisk/GSI/vendor hashes, boot conditions, observed output and the route back to a known-good image. Track subsystem results in the [compatibility matrix](docs/COMPATIBILITY_MATRIX.md) and use the [driver dependency map](docs/DRIVER_DEPENDENCY_MAP.md) to sequence ports.
